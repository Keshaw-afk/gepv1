# GEPV1 — Minimal Architecture

**GEPV1 (General Environment Programming Engine V1)**: a teacher draws a stage with drag and
drop, writes a short Lua script that drives it, and gets a video.

This document describes a **deliberately small V1**: just enough to run one example end-to-end
and show every step of the process. Source notes: [`idea.txt`](idea.txt).

---

## 1. Scope

**In V1**
- **GUI editor (web page):** a tool row (select, circle, rectangle, triangle, text, line, arrow);
  drag and drop the starting picture, then save the stage
- **GUI steps:** build behaviour without code: colour, move, pause, and objects that appear,
  connect, resize and disappear while it plays; in sequence or together
- Shapes: `circle`, `rect`, `triangle`, `text`; lines and arrows between them
- Lua API: `node`, `rect`, `triangle`, `text`, `edge`, `arrow`, `color`, `move` (linear or
  `"smooth"`), `size`, `remove`, `wait`, `pos`, `neighbors`, `edge_of`
- **Editing comforts:** lasso and multi-select, group move, resize handle, align and spread, duplicate,
  copy/paste, nudge, snap-to-grid, a coordinate guide (`opts.coords` in core/svg.js, editor only; remembered in localStorage `gepv1.coords`), undo/redo and autosave (`web/history.js`, localStorage)
- In-page preview that works in **frames** (the MP4's frames), **moments** (frames where a change
  has just finished, with the step or line that made it) and a trace of every pipeline stage
- Output: **MP4 video** (SVG frames encoded by ffmpeg), **animated SVG** (one self-playing file),
  and a still SVG of any frame. Size, frame rate, font and background are adjustable

**Not in V1:** plugins, loops/conditions in the GUI steps, LLM translation.

**Technology:** JavaScript (ES modules) for the engine and the web page; Lua runs in the
**Fengari** VM (Lua 5.3 written in JS), so the same engine code runs in the browser and in Node.

---

## 2. Pipeline

```
 GUI editor ──► stage.lua  ─┐                                                ┌─► SVG frames ─► MP4
 GUI steps  ──► steps.lua  ─┼─► Lua API ─► Commands ─► Timeline ─► Player ───┤   (ffmpeg)
 teacher    ──► script.lua ─┘   (Fengari)  (records)   (sorted, t)  (scene at t)└─► animated SVG
```

Each stage has a single, inspectable output, and the **trace** prints what each one produced.
That makes the demo easy to explain.

| Stage | Input | Output |
|-------|-------|--------|
| **GUI editor** | teacher's drag and drop | `stage.lua` (plain API calls) |
| **GUI steps** | clicks, colour picks, drags | `steps.lua` (plain API calls) |
| **Lua API** | `stage.lua` + `script.lua` | calls such as `color(A, "red")` |
| **Commands** | API calls | data records `{op, id, prop, value, t, dur, src}` (`src` = file and line) |
| **Timeline** | commands | commands in start-time order, script clock in integer ms |
| **Player** | timeline + time `t` | scene state at `t` (interpolated) |
| **Frames** | timeline + fps | frame `i` at `i/fps`, the last one at or after the end; moments |
| **SVG renderer** | scene state | one SVG document per frame |
| **Video export** | SVG frames | `out.mp4` |
| **Animated SVG** | timeline (resolved tweens) | one `.svg` with `<animate>`/`<set>` elements |

## 3. Core ideas

**Object = properties + API** *(from idea.txt)*
Every shape is an object with an `id` and properties (`label`, position, `color`).
Scripts change objects only through the API.

**One backend for the GUI and scripts** *(from idea.txt)*
The editor does not have its own file format. It saves the stage as **Lua code made of the same
API calls a teacher would write**, and loading a stage means running it:
```lua
-- stage.lua (generated by the GEPV1 editor)
A = node("A", 100, 180)
B = node("B", 270, 90)
C = node("C", 270, 270)
D = node("D", 440, 180)
edge(A, B)
edge(A, C)
edge(B, D)
```
Labels that aren't safe Lua names (spaces, keywords, API names, duplicates) get a variable
such as `node_1`. The label itself is kept as a string.

**GUI steps are code too** *(idea.txt: "define the behaviour we want using GUI, and leave the code
part to the system")*. The steps list keeps a list of steps and generates `steps.lua`; the engine
runs stage.lua → steps.lua → script.lua in one Lua state, one clock. The steps list also shows what
script.lua does, read-only, under the steps: one row per moment a change finishes (grouped like
Moments, at most 200 rows), and clicking one shows `sceneAt(t)` of the full run in the editor's
`view` mode (nothing can be selected or changed; `codeAt` in `web/app.js`). A script error shows
in the list instead of the rows:
```lua
-- steps.lua (generated by the GEPV1 steps editor)
color(A, "red", 0.5)
color(edge_of(A, B), "red", 0.5); wait(0.5)   -- "with previous": one shared wait
move(B, 403, 40, 0.5); wait(0.5)
E = rect("E", 520, 120)                       -- an object that appears at this step
arrow(B, E)
remove(edge_of(A, C))
tree_layout(A, 0.5); wait(0.5)                -- glide the tree into tidy rows
```
While building steps, the canvas shows the stage *after* the steps, computed by the same engine,
with faint trails where things moved. Objects that steps create have their own ids (`s1`, `s2`, …;
stage objects have numbers), so later steps can colour, move or remove them. A step stays only
while its object exists at that point in the list: deleting the step that added an object also
deletes the steps that used it.

**Frames are the unit** *(the page, the CLI and the MP4 agree)*
Frame `i` is at `round(i × 1000 / fps)` ms, and the last frame is at or after the end, so the
finished picture is always a frame (DFS: 109 frames, 0 to 108, the last at 4.32 s). Frame 43 in the
page is `frame_00043.svg` from `--frames`, `--frame 43` in the CLI and the 44th picture of the MP4.
A **moment** is the first frame at or after a change ends; each moment names what changed and where
it came from (`Step 3`, `script.lua:6`).

**Exported SVG is meant to be reused**
Every object has an id and a class, shared styling is one `<style>` block, one element per line.
Every shape is drawn around its centre and placed with one `translate()`, so a move is one
transform whatever the shape:
```svg
<line id="A-B" class="edge" x1="100" y1="180" x2="270" y2="90" stroke="#e53935"/>
<polyline id="B-E" class="edge arrow" points="270,90 395,105 520,120" stroke="#888888" marker-mid="url(#arrowhead)"/>
<g id="A" class="node circle" transform="translate(100 180)">
  <circle r="24" fill="#e53935"/>
  <text y="6" fill="#ffffff">A</text>
</g>
```
An arrow is a polyline through its middle, where the arrowhead sits (a marker that takes the
arrow's colour). Ids are the labels (`A`, `A-B`), or `node-3` when a label isn't a safe id (`5`,
`p 1`, a duplicate). They are computed once from every object the timeline ever creates
(`timelineIds`), so they are the same in every frame, also after objects are removed. The page
itself draws an *inline* flavour without ids or `<style>` (inline SVG shares the page's DOM). Both
flavours give identical pixels in librsvg; compared with v1.0.0 (`cx`/`cy` instead of
`translate()`), 4 of 89 sampled frames differ by at most 2 in a colour channel (anti-aliasing).

**Record, then play**
A script runs instantly, but the animation takes time. So API calls don't draw anything.
They append commands to a timeline at the current *script clock*:
- Verbs (`color`, `move`) start at the current clock and last `dur` seconds (default 0.5 s).
- Creating and removing are instant: `create` and `remove` commands.
- `wait(t)` advances the clock by `t`.

Each command also records the object's name at that moment (`cmd.name`) and the line that made it
(`cmd.src`), so traces and moments read well after the object is gone.

The player then computes the scene at any time `t`:
`scene(t)` = every command whose start time is `≤ t`, applied in order. A command that is
still in progress is interpolated: colours blend; positions move linearly, or along the
`"smooth"` curve (CSS `ease-in-out`, the same curve SMIL uses in the animated SVG). A new tween
starts from wherever the property currently is, so a move can change direction mid-move.

**Movement is ordinary moves**
`pos(id)` tells a script where a node is right now (also halfway through a move).

`size(id, w, h, dur?, ease?)` scales a node about its centre like a colour change: a width and a height
factor, 0.25 to 5 (`size(id, s)` = both). Values are `{ w, h }` (a plain number still reads as both). The
label never stretches: it scales by the smaller factor, and so does a text shape. Static SVG: a uniform size
is `scale(s)` on the node's `transform` (only when not 1); a stretched one puts `scale(w h)` on the outline
and `scale(min)` on the label. The animated SVG always animates those two (outline and label), so a size
never fights the move on the group; where width and height cross over during a tween the label's scale is
sampled every 10 ms plus the exact crossing.

**Stage colours:** `stage.lua` writes `color(A, "red", 0)` after the shapes. In stage.lua only, an instant
colour on an object created at that moment becomes its starting colour (the create command's colour), so
it is no change in the timeline, no moment and no trace line.

## 3b. Built by an AI (tools, plugins, MCP, assistant)

GEPV1's aim is **academic animations built by an AI** through a procedure we provide. The AI never writes
Lua; it calls tools that write the same scene + keyframe steps as the GUI, so the result is editable.

The user types plain step-by-step instructions and the AI may be very small (qwen3 0.6B), so the
model's job is kept to "pick the verb and the object"; everything else is done in code.

- `core/ai_tools.js`: the 12 tools (`TOOLS`): `draw`, `write`, `move`, `color`, `resize`, `connect`,
  `remove`, `rename`, `wait`, `undo`, `clear`, `show`. Also `runTool(project, name, args)`,
  `describeProject`, `briefState` (one line of what exists), `findMany`, and `RECIPE` (rules plus
  sentence → call examples; the MCP instructions and the system prompt).
  - A project is `{ scene, steps, last, selected, fresh, history }`.
  - **No modes.** Each call happens after the previous one (a keyframe of its own); `together: true`
    joins the previous keyframe; instant changes (appear, connect, disappear) join a run of instant
    ones. Before anything has happened, drawing builds the starting picture. `seconds` is on the
    action (0.1–60; an explicit `dur` is kept inside a joined keyframe). Changes go through `recordSteps`.
  - **Pointing:** `label` may be a name, a list, "A, B and C", "all circles", "the red ones",
    "everything", "it"/"them" (`last`), "selected"/"these" (`selected`, the Stage selection). A set
    changes together; a moved set keeps its arrangement. Unnamed shapes are "circle 1", "box 2"…
    (stable: counted over everything ever made); "the circle" works when there is one.
  - Colour, size or removal of a shape the AI **just drew** (`fresh`, starting picture only) describes
    the starting picture; for anything already there it is something that happens (animated).
  - `move` takes x/y (to) or right/left/up/down (by), `arc` (true or px), `via` points.
  - Forgiving arguments (numbers as text, "square", "light grey", aliases such as add→draw,
    delete→remove); errors (`ToolError`) say how to fix the call; replies give the times
    ("from 0 to 3 s"). `undo` uses `history`; a plugin's own calls make one undo step.
- `core/instructions.js`: `splitInstructions` (sentences, ";", "then", "and at the same time", "and
  draw…"; never inside brackets or at a bare "and"); `fromWords(step, tool, args, names)`: the
  user's words override the model's guesses: together only when said, seconds as said, "by 100 to
  the right", "these"/"them"/"everything"/"the boxes", the colour said last, the object named,
  and for `draw` the shape, label, colour, place and size typed (nothing the user didn't say: no
  colour, no (0, 0), no shape word as a label); a made-up object name becomes the one named, "the
  circle" or "it"; `rename` from "name the circle Bomb" / "call it queue" / "rename A to B"; sizes in
  pixels for `resize` ("radius 60", "increase its radius by 50", "100 pixels wider" → `radius`,
  `add_size`, `add_width`, `add_height`, which `sizeFrom` turns into factors);
  `toolFromWords` (the tool the words plainly ask for: connect, rename, resize, remove, color);
  `obviousCall` for simple instructions a model won't call ("hide it", "wait 2 seconds", renames
  and pixel resizes). The loop refuses a `color` call when the instruction names no colour. "centre"/"middle" =
  (320, 180) for move and draw; `color` takes `times` ("6 times": one change after another) and
  "different"/"random"/"rainbow" colours, which cycle through colours other than the current one
  (a named colour with `times` flashes: red, back, red).
- `core/ai_loop.js`: `carryOut(message, {ask, run, brief, names, on, stopped})`. One instruction at a
  time, each in a fresh short conversation (system prompt + what exists + the instruction). A failed
  call goes back with its error (2 retries); a working call ends the instruction (so the model can't
  add steps), unless it names more places "(x, y)" than were drawn. Repeated identical calls are dropped.
- `tools/ai_eval.mjs`: runs prompts in the user's style through `carryOut` against a model (default
  qwen3:0.6b on Ollama) and checks the end state and timing; three sets (tuned on, held out, fresh).
- `core/plugins/`: `make_row`, `make_tree`, `make_graph`, `swap`, `throw`. Each one is built only from
  the core tools (`runTool`), and importing `core/plugins/index.js` registers them.
- **Live link** (`node/server.js`): the open tab owns the project.
  - A tool call (`POST /api/tool`) is sent to the newest tab over server-sent events (`GET /api/live`).
    The tab runs it with `runAiTool` in web/app.js (one undo step, an "AI is editing" note) and posts
    the reply to `/api/tool-result`.
  - With no tab open, the server runs `xdg-open` on the app and waits 10 s.
  - `show` also returns the end picture: the tab renders the SVG and the server rasterises it with
    ffmpeg (librsvg) into a PNG.
  - `/api/*` only accepts JSON from this app's origin, or from a program with no Origin header.
- `node/mcp.js`: the MCP server (stdio, `@modelcontextprotocol/sdk`). It lists `TOOLS` with plain JSON
  schemas, uses `RECIPE` as its instructions, forwards calls to `/api/tool`, and starts the app server
  (detached) if nothing answers.
- `web/assistant.js`: the in-app chat: `carryOut` with the OpenAI chat API through `POST /api/llm`
  (relayed by the server), running tools with `runAiTool` (web/app.js keeps `last`, `fresh` and
  `history` between calls until the user edits by hand, and passes the Stage selection). Settings
  are kept in localStorage `gepv1.assistant`.
  - For local servers (localhost) it sends `reasoning_effort: "none"`: small models are far faster and
    call tools reliably without reasoning first.
  - Instructions that got no working call are listed at the end ("Not done: …").
- The Build list shows one duration per keyframe; when its changes last different times (an AI's
  `together` with its own seconds), each timed change gets its own field.

**Script safety:** only Lua's base, table, string and math libraries are loaded (no `io`, `os`,
`require`, `dofile`). An instruction limit stops infinite loops so they can't freeze the page.

**GUI editor actions**

| Action | At Start (the starting picture) | At a step (becomes a step inserted there) |
|--------|-------|----------------------------|
| Tool row: select `V`, circle `C`, rectangle `R`, triangle `T`, text `X`, line `L`, arrow `A` | | |
| Shape tool, click empty canvas | Add that shape (auto label `A`, `B`, …; text asks for its words) | The object appears |
| Drag an object | Move it | Record a move (a bent drag: a curved move) |
| Line or arrow tool (or Shift-drag) from one object to another | Connect them | They get connected |

| Ctrl/Cmd-click, Ctrl+A | Add to / toggle the selection; select all | same |
| Pick a colour | Colour the selection (starting colour) | Colour steps |
| Handles (right = width, bottom = height, corner = both, Shift = keep shape), W and H fields | Change size | `size` steps (all selected together) |
| Align / spread buttons (overlapping objects are moved apart the other way, 30 px gap) | Move the nodes now | Move steps together |
| Duplicate, Ctrl+C / Ctrl+V | Copy of the nodes and lines between them | `add` + `connect` steps |
| Delete key / Delete or Remove button | Delete the selection (with its lines) | The objects disappear |
| Arrow keys (Shift: 10 px), `G` | Nudge; snap to grid | Snap only |
| Ctrl+Z / Ctrl+Shift+Z | Undo / redo the whole project | same |
| Double-click / the Label field | Rename | Rename an object a step added |
| `Ctrl+S` / `Ctrl+O` | Save or load `stage.lua` | |

**One Build tab, a point in the steps.** The steps list starts with a **Start** row; the page keeps
`point` (0 = Start, k = after the first k steps) and a mode, **Arrange** or **Record**. Arrange at 0: the
editor is in `'stage'` mode and edits `core/Scene`. Otherwise it is in `'behaviour'` mode and shows the
picture after `steps.slice(0, k)` (built and run like any program); Record splices new steps in at k,
Arrange adjusts instead of recording: `sourceOf(steps, k, id, prop)` (core/steps.js) finds the step that
decides pos/size/colour there (or -1 = the stage) and that step or the stage changes (`reshapePath` bends a
curved move to a new end; an object a step added gets an instant colour step right after it). A new
object, line or paste in Arrange after the start is recorded anyway, as an appearance at k: anything
else would make it exist from 0 s, before the moment shown.
**Keyframes:** steps whose `together` flag is set play with the one before; a run of them is a keyframe
(`keyframes()` in core/steps.js, a pause is one on its own). The point always sits at a keyframe's end
(`keyframeEndAt`). Record goes through `recordSteps(steps, point, changes, {join, appearAtEnd})`: changes join the
keyframe ending at the point (taking its duration) unless "Next keyframe" asked for a new one; with
`appearAtEnd` (the GUI) something that only appears does not join a keyframe where things take time
(it would pop up at its start, before the picture shown) but gets its own keyframe at the point; a second
change to the same object's position merges into one `path` step, a colour or size replaces. Removing or
pruning steps keeps every other step in its keyframe (`keepKeyframes`, `removeStep`).
**Curved moves:** in Record a drag that strays 8 px or more from a straight line keeps its shape
(simplified with `simplify()` in `core/paths.js`) and becomes `path(id, {{x, y}, …}, dur)`. Lua smooths the
points (centripetal Catmull-Rom, `smoothPath`) and stores the curve in the command; the player and `pos()`
follow it at even speed (`pointAlong`), the animated SVG uses its corners as `values`/`keyTimes`. `prune()` keeps the point on the same step and
tells the user when steps that used a removed object were dropped. What happens over time comes from
the steps (sequences without code) and/or `script.lua` (loops, algorithms).

**Animated SVG:** each resolved tween becomes an `<animate>` (an instant change becomes a `<set>`).
A move is an `<animateTransform type="translate">` on the object's group (smooth moves use
`calcMode="spline"` with the same curve) plus `<animate>` on the ends of every line touching it.
An arrow's points depend on both ends, so they are sampled every 10 ms while either end moves.
Objects created later start hidden; removed ones are hidden from then on. When animations overlap,
the later one wins, as in the player. It uses the same ids, classes and `<style>` as a still frame.
It was checked in
Chrome against the player every 23 ms for the DFS, network, edge-case, size, curve and stretch scripts (20,337 checks: position, colour and visibility of every object,
arrow points). It matched everywhere except exactly on a command's start instant, where Chrome's
clock is half a millisecond off. It plays once.

**Video export:** ffmpeg, with no custom encoder. ffmpeg's built-in librsvg decoder reads the
SVG frames directly:
```sh
ffmpeg -framerate 25 -i frame_%05d.svg -c:v libx264 -pix_fmt yuv420p out.mp4
```
The scene is drawn in 640×360 units (`viewBox`); the output size is 1×, 2× or 3× that, so it is
always even, which the H.264 / `yuv420p` encoder requires. Video frames always have an opaque
background (a transparent one becomes white), because otherwise transparent areas encode as black.

## 5. Lua API (complete V1 surface)

The user-facing reference, with arguments, timing, limits, errors and examples, is
[docs/LUA_API.md](docs/LUA_API.md). `test/lua_api_doc.test.js` runs every example in it.

```lua
node(label, x, y)       -- create a circle with a text label; returns id
rect(label, x, y)       -- a rounded rectangle with a label
triangle(label, x, y)   -- a triangle with a label
text(words, x, y)       -- just text (color() colours the text)
edge(a, b)              -- create a line between two objects; returns id
arrow(a, b)             -- a line with an arrowhead in the middle, pointing from a to b
color(id, c, dur?)      -- animate colour to c ("red", "#ff0000", ...)
move(id, x, y, dur?, ease?)  -- animate position to (x, y); ease "linear" (default) or "smooth"
path(id, {{x, y}, …}, dur?, ease?) -- a curved move from where it is through the points, smooth, at even speed
remove(id)              -- the object disappears (a node takes its lines with it)
wait(t)                 -- advance the script clock by t seconds
pos(id)                 -- x, y of a node right now (also halfway through a move)
neighbors(id)           -- list of nodes connected to id (edges are undirected, creation order)
edge_of(a, b)           -- id of the edge between a and b, or nil
size(id, w, h, dur?, ease?) -- width and height factors about the centre (0.25 to 5, 1 = normal); size(id, s) = both
                        --   node(label, x, y, w?, h?) and rect/triangle/text start at a size
print(...)              -- shown in the trace
```

With `neighbors` and `edge_of`, a script works on **whatever graph the teacher drew in the
GUI**. The algorithm doesn't need its own copy of the graph.

## 6. Demo example: DFS on a 4-node graph

**Step 1: draw in the GUI.** Place nodes A, B, C, D, connect A–B, A–C, B–D. This is the
`stage.lua` shown in §3, and the page starts with it loaded.

**Step 2: write the behaviour.** `examples/dfs.lua`:
```lua
local visited = {}
local function dfs(v)
  visited[v] = true
  color(v, "red"); wait(0.5)
  for _, n in ipairs(neighbors(v)) do
    if not visited[n] then
      color(edge_of(v, n), "red"); wait(0.3)
      dfs(n)
    end
  end
  color(v, "black"); wait(0.3)          -- finished
end
dfs(A)
```

**Step 3: run.** In the page, pick **Load example… → Depth-first search** in the Code tab and press **Run**, then **MP4 video** or **Animated SVG** in the Result tab. Or from the CLI:
`node node/cli.js examples/stage.lua examples/dfs.lua --trace --video out/dfs.mp4`
```
[stage]     4 nodes, 3 edges (from stage.lua)
[commands]
  t=0.00  create node A (100,180)         stage.lua:2
  …
  t=0.00  set A.color -> red  dur=0.50    script.lua:6
  t=0.50  set A-B.color -> red  dur=0.50  script.lua:9
  t=0.80  set B.color -> red  dur=0.50    script.lua:6
  …
[timeline]  18 commands (7 create, 11 set), total 4.30 s
[player]    t=0.25  A.color = #d98381  (halfway to red)
[svg]       109 frames at 25 fps
[video]     out/dfs.mp4 (ffmpeg)
```
