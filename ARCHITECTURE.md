# GEPV1 — Minimal Architecture

**GEPV1 (General Environment Programming Engine V1)**: a teacher draws a stage with drag and
drop, writes a short Lua script that drives it, and gets a video.

This document describes a **deliberately small V1**: just enough to run one example end-to-end
and show every step of the process. Source notes: [`idea.txt`](idea.txt).

---

## 1. Scope

**In V1**
- **GUI editor:** drag and drop nodes and edges, then save the stage
- Shapes: `circle`, `line`, `text`
- Lua API: `node`, `edge`, `color`, `move`, `wait`, `neighbors`, `edge_of`
- Output: SVG frames → **MP4 video** (converted with existing tools)

**Not in V1:** forces/physics, plugins, behaviour editing in the GUI, live preview,
LLM translation.

---

## 2. Pipeline

```
 GUI editor ──► stage.lua ─┐
                           ├─► Lua API ─► Commands ─► Timeline ─► Player ─► SVG frames ─► MP4
 teacher    ──► script.lua ┘   (C+Lua)    (records)   (sorted, t)  (scene at t)  (frame_000.svg …)  (rsvg-convert + ffmpeg)
```

Each stage has a single, inspectable output. That makes the demo easy to explain, because the
engine can print what each stage produced.

| Stage | Input | Output |
|-------|-------|--------|
| **GUI editor** | teacher's drag and drop | `stage.lua` (plain API calls) |
| **Lua API** | `stage.lua` + `script.lua` | calls such as `color(A, "red")` |
| **Commands** | API calls | data records `{op, id, prop, value, t, dur}` |
| **Timeline** | commands | commands sorted by start time `t` |
| **Player** | timeline + time `t` | scene state at `t` (interpolated) |
| **SVG renderer** | scene state | one SVG file per frame |
| **Video export** | SVG frames | `out.mp4` |

## 3. Core ideas

**Object = properties + API** *(from idea.txt)*
Every shape is an object with an `id` and typed properties (`x`, `y`, `r`, `color`, `label`).
Scripts change objects only through the API.

**One backend for the GUI and scripts** *(from idea.txt)*
The editor does not have its own file format. It saves the stage as **Lua code made of the same
API calls a teacher would write**:
```lua
-- stage.lua (generated by the GUI)
A = node("A", 100, 100)
B = node("B", 250,  50)
C = node("C", 250, 150)
D = node("D", 400, 100)
edge(A, B); edge(A, C); edge(B, D)
```
So the GUI is just another way to produce API calls, and the teacher can read or hand-edit the
result.

**Every API call becomes a command**
A command is plain data, so it can be logged and replayed.

**Record, then play**
A script runs instantly, but the animation takes time. So API calls don't draw anything.
They append commands to a timeline at the current *script clock*:
- Verbs (`color`, `move`) start at the current clock and last `dur` seconds (default 0.5 s).
- `wait(t)` advances the clock by `t`.

The player then computes the scene at any time `t`:
`scene(t)` = initial objects + every command whose start time is `≤ t`. A command that is
still in progress is interpolated: colours blend and positions move linearly.

## 4. Components

**Engine** (C, embedded Lua): command-line program `gepv1`

| Component | Responsibility |
|-----------|----------------|
| `scene` | Array of objects (id, type, properties) and the edge list |
| `command` | Command record + append to timeline |
| `timeline` | Sorted command list, script clock, `wait` |
| `player` | `scene_at(t)`: apply and interpolate commands |
| `svg` | Write one scene state as an SVG file |
| `lua_api` | Binds the Lua API (§5) to the C core |
| `export` | Calls the external tools to turn frames into a video |
| `main` | Run `stage.lua` then `script.lua` → timeline → frames → video |

**GUI editor:** a separate small C program, `gepv1-editor`, built with **raylib** (proposed:
simple 2D drawing and mouse input, single C library)

| Action | Result |
|--------|--------|
| Click empty canvas | Add a node (auto label `A`, `B`, …) |
| Drag a node | Move it |
| Drag from one node to another (right mouse button) | Add an edge |
| Double-click a node | Rename its label |
| `Delete` key | Remove the selected node or edge |
| `Ctrl+S` / `Ctrl+O` | Save or load `stage.lua` |

The editor only edits the **initial layout**. Behaviour (what happens over time) stays in
`script.lua`, as in idea.txt: "Initial GUI state ⇒ purely teacher drag and drop … behaviour ⇒ code".

**Video export:** existing tools, no custom encoder

| Tool | Job |
|------|-----|
| `rsvg-convert` (librsvg) | SVG frame → PNG |
| `ffmpeg` | PNG sequence → MP4 |

```sh
for f in frames/*.svg; do rsvg-convert "$f" -o "${f%.svg}.png"; done
ffmpeg -framerate 25 -i frames/frame_%03d.png -c:v libx264 -pix_fmt yuv420p out.mp4
```
`gepv1 --video out.mp4` runs these two steps. The canvas size must be even (e.g. 500×200),
because the `libx264` encoder with `yuv420p` requires even dimensions.

## 5. Lua API (complete V1 surface)

```lua
node(label, x, y)      -- create a circle with a text label; returns id
edge(a, b)             -- create a line between two nodes; returns id
color(id, c, dur?)     -- animate fill/stroke colour to c
move(id, x, y, dur?)   -- animate position to (x, y)
wait(t)                -- advance the script clock by t seconds
neighbors(id)          -- list of nodes connected to id (in edge creation order)
edge_of(a, b)          -- id of the edge between a and b
```

With `neighbors` and `edge_of`, a script works on **whatever graph the teacher drew in the
GUI**. The algorithm doesn't need its own copy of the graph.

## 6. Demo example: DFS on a 4-node graph

This example exercises every stage: drawing in the GUI, API calls, timing and interpolation,
rendering, and video export.

**Step 1: draw in the GUI.** Place nodes A, B, C, D, connect A–B, A–C, B–D, and save. This
produces the `stage.lua` shown in §3.

**Step 2: write the behaviour.** `script.lua`:
```lua
local visited = {}
local function dfs(v)
  visited[v] = true
  color(v, "red"); wait(0.5)
  for _, n in ipairs(neighbors(v)) do
    if not visited[n] then
      color(edge_of(v, n), "red"); wait(0.3)
      dfs(n)
    end
  end
  color(v, "black"); wait(0.3)          -- finished
end
dfs(A)
```

**Step 3: run.** `gepv1 stage.lua script.lua --trace --video dfs.mp4`
```
[stage]     4 nodes, 3 edges
[commands]
  t=0.0  set A.color   -> red   dur=0.5
  t=0.5  set A-B.color -> red   dur=0.5
  t=0.8  set B.color   -> red   dur=0.5
  …
[timeline]  18 commands (7 create, 11 set), total 4.3 s
[player]    t=0.25  A.color = 50% grey→red
[svg]       frames/frame_000.svg … frame_107.svg  (25 fps)
[video]     dfs.mp4  (rsvg-convert + ffmpeg)
```

The result, `dfs.mp4`, shows the traversal colouring nodes and edges step by step.

---

## 7. Build order

1. `scene` + `svg`: draw static nodes and edges to one SVG.
2. `command` + `timeline` + `player`: produce frames from hard-coded commands in C.
3. `lua_api`: drive the same thing from `stage.lua` + `script.lua`.
4. `export`: frames → MP4 via `rsvg-convert` + `ffmpeg`.
5. `gepv1-editor`: drag and drop that saves `stage.lua`.
6. `--trace` output and the DFS demo end-to-end.

The editor comes after the engine because it only needs to write a file the engine already reads.
