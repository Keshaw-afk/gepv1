# GEPV1 TODO

What defines GEPV1: **SVG output**, **Lua code generated by the GUI**, and **any frame as an SVG**.
Usability work is judged by how well it serves those three.

## Now: shapes and motion (big change)

Three kinds of motion on one engine, all ending up as ordinary frames:
**scripted** (`move`, now with easing), **automatic layout** (tidy tree, force-directed settle) and
**forces** (one general mechanism, designed with the user first). Objects can also appear, connect and disappear *during* the behaviour, from
code and from the Steps tab, not only on the Stage.

### 1. Shapes
- [ ] `rect(label, x, y)`, `triangle(label, x, y)`, `text("Hello", x, y)` next to `node` (circle);
      `arrow(a, b)` next to `edge(a, b)`. Every shape can be coloured, moved, connected, pushed.
- [ ] SVG: each object is `<g id class="node rect" transform="translate(x y)">`, so a move animates
      one transform for any shape; arrows are a `<polyline>` with a mid-arrow marker (`context-stroke`,
      checked in librsvg). Re-check: existing examples give identical pixels.
- [ ] Stage editor: an icon toolbar on the canvas (circle, square, triangle, text; line or arrow);
      stage.lua saves the new calls.

### 2. Appear, rewire, disappear
- [ ] `remove(id)` (a node takes its lines with it); objects created mid-script already appear later.
- [ ] Player, animated SVG, moments ("p1 disappears") and the trace handle removal.

### 3. Scripted and layout motion (do first: the user's example is a tree reorganising)
- [ ] Easing: `move(id, x, y, dur, "smooth")` (ease-in-out; linear stays the default so old outputs don't change).
- [ ] `pos(id)`: where an object is at the current script time (also mid-move, also under physics).
- [ ] `tree_layout(root, dur?)`: every node of the tree glides to tidy tree positions (children
      left to right by x), so a rotation is "rewire, then tidy".

### 4. Forces: one general mechanism (design to be agreed first)
- [ ] Not a catalogue of physics forces. Objects can have a velocity; a **rule** (a few lines of Lua,
      or a ready-made one picked in the GUI) changes it over time. Gravity, springs or "pull towards
      a target" are just examples of rules.
- [ ] Runs in step with the script clock on a fixed grid and is baked into frames, so every frame
      stays exact and `pos()` works mid-motion.
- [ ] Show the design to the user before building it.

### 5. Behaviour (Steps) gets the same powers
- [ ] Canvas toolbar in Behaviour: Select (drag = move), shapes (click = the object pops in at this
      step), **Connect** (drag node to node). (A Push tool comes with 4.)
- [ ] Context actions for the selection: colour, Remove, Tidy tree from here (force actions come with 4).
- [ ] Objects created by steps can be targeted by later steps; deleting a step removes what depends on it.

### 6. Lively, still uncluttered
- [ ] Icon toolbar with the active tool in the accent colour; the deck's red as a second accent for forces.
- [ ] New objects pop in; motion trails in the preview (toggle, never exported).
- [ ] Screenshot every tab; check for clutter.

### 7. Examples, docs, tests
- [ ] Examples: tree rotation (rewire + tree_layout), shapes (network: routers and packets);
      force examples once 4 is agreed.
- [ ] README, ARCHITECTURE (shapes, motion, physics, API) and this file updated as each phase lands.
- [ ] Tests per phase; commit per phase (local), push when asked.

## Done: exported SVG, code viewer, frames, landmarks

### A. Exported SVG you can reuse
- [x] Every object is identifiable: `<g id="A" class="node">` (circle + label), `<line id="A-B" class="edge">`.
      Ids follow the labels (`A`, `A-B`), falling back to `node-3` when a label isn't a safe id.
- [x] Shared styling in one `<style>` block (stroke, font) so elements are short and can be restyled with CSS.
- [x] One element per line, indented (the Wrap toggle avoids sideways scrolling in the narrow panel).
- [x] Still frames say what they are: `<!-- GEPV1 frame 43 / 108, t = 1.72 s -->`.
- [x] The animated SVG uses the same ids, classes and style.
- [x] Check the video still matches: render frames with ffmpeg/librsvg (CSS support) against the old renderer.

### B. Fixed → adjustable output
- [x] Output settings (collapsed in Result): **size** (1×, 2×, 3× → 640×360, 1280×720, 1920×1080),
      **background** (colour, or transparent for SVG), **font** (sans-serif, serif, monospace), **frame rate**.
- [x] The same settings drive the preview, This frame, Animated SVG and MP4 (server accepts them).
- [x] Transparent background: SVG only; MP4 falls back to white (H.264 has no alpha).

### C. Code viewer
- [x] One small viewer for every generated block (stage.lua, steps.lua, SVG of this frame, trace).
- [x] **Copy**, **Save** (download with a sensible filename), **Wrap** toggle.
- [x] Basic highlighting for Lua and SVG. (Line numbers skipped: not needed yet.)
- [x] Save for the Code tab (script.lua), so every piece of code can leave the page.

### D. Frames as a real concept
- [x] The slider moves frame by frame on the video's grid (fps), not in milliseconds.
- [x] Show `Frame 43 / 108 · 1.72 s` (0-based, like the file names); type a frame number to jump.
- [x] ‹ › buttons, ←/→ keys (Shift = 10 frames), Home/End, Space to play/pause.
- [x] Playback shows exactly the frames the MP4 will have; the last frame is the finished picture

- [x] This frame saves `frame_00043.svg`: same frame and name as `--frames` in the CLI.
- [x] Returning to Result keeps your frame when nothing changed; a changed program starts from 0.
- [x] CLI: `--frame N OUT.svg` writes one frame.

### E. Landmarks
